# excel-parity-check

This is a piece of a tool I built at work, rewritten so you can run it. It checks that an Excel file generated by an app shows the same numbers as the app's data. It recalculates every formula in the file the way Excel does when it opens it, compares each cell with the expected value, and fails if even one cell has a difference nobody can explain.

## The check that passed while the file was wrong

The original is an internal revenue tool for a certification body. I built it alone, as an employee, mostly in Claude Code sessions. This repo rewrites one part of it on invented data, so you can read and run it in a few minutes. None of the real code, file layout or data is in here.

Before the tool, the company tracked revenue every week in big shared Excel workbooks. Each area manager typed numbers into their own sheet, and formulas added everything up across sheets and files. The tool replaced that: people enter numbers in a web grid, the database is the source of truth, and the app generates the Excel files in the old layout, because people still read them. So every week the question is: does the generated file show what the database says?

My first version of the check compared only the input cells, the numbers the app writes into the file. They were right, so the check passed, but the file was wrong: on one sheet the month total row had no formula. The inputs were there and nothing added them up, so every total built on that row was too low. Nobody noticed, because the check only looked at the cells the app writes.

Reading the values saved in the file doesn't help either. A generated file usually carries stale saved results next to its formulas and tells Excel to recalculate on open, so those saved numbers say nothing about what the user will see. The only way to see that is to recalculate the file yourself. When I added the recalculation it found 48 unexplained cells on one sheet, while the earlier checks were green.

## How the file is recalculated and compared

```text
 expected.json                   generated .xlsx
 (stands in for the database)    (formulas + stale saved values)
        |                                   |
        |                          read with zipfile + xml
        |                                   |
        |                          formula engine: recalculates
        |                          each cell like Excel on open,
        |                          ignores the saved values
        v                                   v
  expected value for              value the user will see
  each cell (sums computed
  from the source data)
        \                                 /
         \                               /
          compare every cell, found by its row and column labels
                          |
       +------------------+-------------------+
       |                  |                   |
     MATCH              KNOWN            UNEXPLAINED
  within 1 cent    declared cause,      anything else,
                   exact amount         including a cell
                                        we cannot recalculate
                          |
          one UNEXPLAINED cell -> FAIL (exit code 1)
```

The check follows four rules:

- The engine supports only what the files use: `SUM`, `+ - * /`, parentheses, references to other sheets of the same file. Anything else (another function, a link to another file, a cycle, a missing sheet) is an error, and the cell counts as unexplained. Reading such a cell as zero would hide the errors the check is there to find.
- Rows and columns are found by their labels. If a label changes or a row disappears, its cells are reported as unexplained. They are never skipped.
- A known difference has to say why and by how much. It covers a cell only if the cell is off by exactly the declared amount. If the same cell also has a new error, the amounts stop matching and the gate fails. In the real tool the list is meant to stay short: a difference goes on it only after someone has found its cause.
- The expected values don't come from the file. I compute the expected total from the source data. If I took it from the file, a wrong formula would pass its own check.

## Try it in 5 minutes

You need Python 3.9 or newer (tested with 3.13). There are no dependencies to install.

```bash
cd excel-parity-check

# run the tests (standard library unittest)
python -m unittest

# a correct file: passes, and shows one declared difference as KNOWN
python -m parity_check examples/good.xlsx

# the real incident, rebuilt: one month total is empty
python -m parity_check examples/empty_subtotal.xlsx

# the same file with the old check, inputs only: green
python -m parity_check examples/empty_subtotal.xlsx --inputs-only
```

Output of the failing run:

  Seniors!E8       Total / Variance vs budget: expected 1,000, file shows -5,000
  Club total!C6    Events / Month total: expected 7,000, file shows 3,000

The exit code is 0 for PASS, 1 for FAIL and 2 when the command can't run, so you can put it in a script or a CI job.

The examples are the budget of an invented amateur rowing club for one month. There are two area sheets (`Youth`, `Seniors`) and a `Club total` sheet that adds them up. Each sheet has three budget lines and a total column, four week rows, a month total, the budget and the variance against the budget.

| File | What is wrong | Result |
|---|---|---|
| `good.xlsx` | nothing, apart from one sponsor payment booked late (declared in `known_differences.json`) | PASS |
| `empty_subtotal.xlsx` | one month total cell is empty | FAIL, 8 cells |
| `wrong_reference.xlsx` | one cell of the total sheet points to the wrong week | FAIL, 2 cells |
| `unsupported_function.xlsx` | one month total uses `ROUND`, which the engine refuses | FAIL, 8 cells |

All four files carry the saved values of the correct file, so a tool that trusts saved values would pass all of them. `python examples/make_examples.py` rebuilds them from `expected.json`, and a test checks that the rebuilt files have the same content as the committed ones.

```text
parity_check/
  xlsx.py        read and write .xlsx with zipfile and xml.etree
  formula.py     formula engine (SUM, arithmetic, sheet references)
  layout.py      shape of the example sheets, builds a correct copy
  gate.py        expected values, known differences, classification, verdict
  __main__.py    command line
examples/        expected.json, known_differences.json, four .xlsx files
tests/           unittest suite, written before the code
```

## What stays in the internal tool

The gate I use at work is bigger. I left out everything that describes the original tool or touches its data:

- the database access and the code that generates the real files (here a JSON file plays the database and `layout.py` plays the exporter);
- the model of the real sheets: their names, the labels it recognises, the coordinates, the mapping between database rows and columns. The example layout is invented and much smaller;
- a second check that compares totals inside the database itself, before the file is even opened;
- everything around it in the app: login, access rules, the web grid, the import of the old files, scheduled jobs, deployment and configuration.

The engine is also smaller and supports only what the example needs. When you drag a formula down, Excel writes "shared formulas". The reader doesn't expand them: it flags those cells and the engine refuses them.

## Rules I gave the agent

I built most of the real project in Claude Code sessions, and I gave the agent rules to follow. The rules file says: tests before code, a typed result for every action that changes data, and the audit record written in the same database transaction as the change. I write each decision down before the code, with a pre-mortem. When a decision turns out wrong, I add a new entry that replaces it and says why.

For many tasks a fresh subagent did the work, then two reviews followed: does it match the spec, and is the code good. I had a different model review the architecture and went through its points one by one. The agents worked inside written boundaries (files they could touch and files off limits), and parallel sessions passed context to each other through shared files.

The parity gate described above came out of that loop. I wrote this extract with Claude Code too, from scratch, with the tests written before the code.

## Limits

- Only `SUM`, `+ - * /` and references inside the same file are supported. Real workbooks often need more (`IF`, `ROUND`, lookups). The rule stays the same: whatever the engine can't recalculate counts as unexplained.
- Shared formulas are refused, so a file saved by hand in Excel will usually fail until the reader learns to expand them. Files generated by code usually write every formula in full.
- The layout is fixed: labels in column A, headers in row 1. The real gate has a richer model of its sheets.
- Number formats, styles and hidden rows are not checked. Only values.
- The tolerance is one cent, absolute.
- A text cell used in plain arithmetic (=A1+1) counts as 0 here. Excel would show an error.
